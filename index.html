  • 그 문서가 6개사 연동 개발의 공통 기준 — 상대 회사들이 이 문서를 보고 자기 앱을 개발
  • 스펙 협의부터 이슈 대응까지 개발자가 전담 — LG유플러스·CJ대한통운·현대커머셜 등과 커뮤니케이션
  • Intent 앱투앱 · 버전 분기로 구현 — 앱 간 오더·경로 전달을 Intent로 잇고, 상대 앱 버전에 따라 동작을 나눠 처리
운영을 멈추지 않고 레거시를 Kotlin · 코루틴으로코드 품질
전면 재작성 없이 Java 앱을 Kotlin 52%까지 — 서비스를 운영하면서
  • 한 번에 새로 짤 수는 없었다 — 3년간 약 1,130개 파일이 쌓인 대부분 콜백 기반 Java 코드베이스. 전면 재작성은 리스크가 크고, 방치하면 유지보수 비용만 계속 느는 상황
  • 기준을 나눴다 — 신규 기능을 만들거나 기존 네트워크 프로토콜을 수정할 때는 코루틴 위주로, 손대지 않는 레거시 콜백은 그대로
  • 수정할 코드에 콜백이 중첩돼 있으면 함께 전환 — 콜백 기반이던 구글 로그인은 Credential Manager 전환과 함께 Firebase의 Task를 await()로 감싸 suspend 흐름으로 정리
  • 신규·수정 API는 처음부터 suspend function — 포인트·다중경유지 상태 조회 등
  • Kotlin 전환도 같은 기준 — 신규 개발은 전부 Kotlin, 레거시는 자주 손대는 코드부터 포팅해 수정할 때마다 null 안전성 확보
  • 뷰 참조 방식도 함께 현대화 — Kotlin synthetic 지원이 끊겨 앱 전역의 뷰 접근을 ViewBinding·DataBinding으로 옮겨야 했다. 한 번에 갈아엎지 않고 화면 단위로 5개월에 나눠 진행
로그에 안 잡히는 크래시를 C++ · 렌더링 계층에서 해결내비게이션 도메인
크래시프리율 99.8%를 받치는 기반 — 원인이 있는 계층에서 근본 해결
  • 왜 안 잡혔나 — 지도 렌더링과 경로 탐색·맵매칭이 모두 C++ 엔진에서 도는 앱이라, 크래시가 Kotlin 스택트레이스에 남지 않는 계층에서 발생
  • 특정 GPU(Adreno)에서만 터지던 지도 크래시 — 렌더링 방식이 원인이어서 client vertex array를 VBO로 마이그레이션해 근본 해결
  • use-after-free — 렌더 스레드가 경로 정점 배열을 읽는 동안 워커 스레드가 그 배열을 해제·교체하던 문제를 정점 배열 전용 락으로 차단
  • shared_ptr refcount 레이스 — 맵매칭의 대입을 std::move로 바꾸고 진입점에 lock_guard를 걸어 해결
  • double-free — 워커 스레드가 중복 생성되던 것을 초기화 재진입 가드로 차단
  • 락 범위는 최소화 — 넓게 걸면 프레임이 끊기기 때문에 의도적으로 좁게 설계
  • C++ 계층의 Protocol Buffers — 경로 응답을 파싱하는 구간의 공유 변수를 제거·분리해 탐색 스레드 간 데이터 불일치를 없앰
  • JNI 양방향 호출 — Kotlin이 엔진을 부르고 엔진이 다시 JVM을 콜백하는 구조라, 그 구간의 스레드 어태치 생명주기(GetEnv → AttachCurrentThread → DetachCurrentThread)까지 처리
백엔드 공백 2개월을 DB · 서버 · 앱 전 구간에서 메움경계 확장
DB 컬럼 추가 → 서버 프로토콜 확장 → 앱 연동까지 맡아 기획 일정 그대로 출시
  • 기다릴 일이 아니라고 판단 — 검색 필터 확장 기획은 확정됐는데 백엔드 담당자가 2개월 장기 부재. 기다리면 로드맵이 그만큼 밀리는 상황이라 직접 하겠다고 나서 승인을 받고 진행
  • 문서에 변경을 남김 — Swagger·DB 테이블 문서에 기록해 복귀한 담당자가 바로 파악할 수 있게
  • 기존 데이터에는 기본값 — 이미 쌓인 데이터에 영향이 가지 않도록 차단
  • 하위 호환을 검증 — 필드가 빠졌을 때 구버전이 정상 동작하는지까지 확인한 뒤 개발서버 선적용을 거쳐 서비스에 반영
주행 중에도 버튼 하나로 — 기사 간 실시간 음성 무전킬러 서비스
녹음·전송·수신·재생을 끊기지 않게 잇는 파이프라인을 설계
  • 주행 중엔 화면도 타이핑도 못 쓴다 — 기사끼리 도로·상하차 상황을 주고받을 방법이 없던 것이 출발점
  • 송수신 파이프라인 전체 설계 — MediaRecorder(AAC) 녹음 → 서버 전송 → 소켓 수신 알림 → MediaPlayer 재생
  • 여러 사람이 동시에 보내도 재생은 하나씩 순서대로 — 수신한 음성을 재생 큐에 쌓고, 큐의 add·poll이 반드시 단일 진입점 하나만 거치게 만든 뒤 락으로 감싸 동시 접근을 차단
  • 재생에 실패한 음성은 큐 앞으로 되돌려 순서를 보존, 큐에 상한을 둬 무전이 몰려도 메모리가 무한히 늘지 않게
  • 별도 백그라운드 스레드가 짧은 주기로 상태를 확인해 다음 음성으로 넘기고, 길안내·통화 음성과 겹칠 때는 오디오 포커스로 조정
  • 녹음·재생 동시 발생, 같은 음성 중복 전송 문제도 이 구조로 정리 — 소켓 재연결, Visualizer 레벨미터까지 구현

  • 결제를 상태머신으로 설계 — 주문 중복 방어, 실패 유형별 복구 플로우
