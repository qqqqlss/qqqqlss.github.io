운영을 멈추지 않고 레거시를 Kotlin · 코루틴으로코드 품질전면 재작성 없이 Java 앱을 Kotlin 52%까지 — 서비스를 운영하면서
  • 한 번에 새로 짤 수는 없었다 — 약 1,130개 파일이 쌓인 대부분 콜백 기반 Java 코드베이스
  • 기준을 나눴다 — 신규 기능을 만들거나 기존 네트워크 프로토콜을 수정할 때는 코루틴 위주로, 손대지 않는 레거시 콜백은 그대로
  • 수정할 코드에 콜백이 중첩돼 있으면 함께 전환 — 콜백 기반이던 구글 로그인은 Credential Manager 전환과 함께 Firebase의 Task를 await()로 감싸 suspend 흐름으로 정리
  • 신규·수정 API는 처음부터 suspend function — 포인트·다중경유지 상태 조회 등
  • Kotlin 전환도 같은 기준 — 신규 개발은 전부 Kotlin, 레거시는 자주 손대는 코드부터 포팅해 수정할 때마다 null 안전성 확보
  • 뷰 참조 방식도 함께 현대화 — Kotlin synthetic 지원 종료로 앱 전역의 뷰 접근을 ViewBinding·DataBinding으로 이전. 화면 단위로 5개월에 나눠 진행
C++ 내비게이션 엔진의 GPU · 멀티스레드 크래시 해결내비게이션 도메인특정 GPU 지도 크래시 · use-after-free · shared_ptr 레이스 · double-free
  • 왜 안 잡혔나 — 지도 렌더링과 경로 탐색·맵매칭이 모두 C++ 엔진에서 도는 앱이라, 크래시가 Kotlin 스택트레이스에 남지 않는 계층에서 발생
  • 특정 GPU(Adreno)에서만 터지던 지도 크래시 — 렌더링 방식이 원인이어서 client vertex array를 VBO로 바꿔 해결
  • use-after-free — 렌더 스레드가 경로 정점 배열을 읽는 동안 워커 스레드가 그 배열을 해제·교체하던 문제를 정점 배열 전용 락으로 차단
  • shared_ptr refcount 레이스 — 맵매칭의 대입을 std::move로 바꾸고 진입점에 lock_guard를 걸어 해결
  • double-free — 워커 스레드가 중복 생성되던 것을 초기화 재진입 가드로 차단
  • 렌더 프레임이 끊기지 않도록 락 범위는 최소로
  • C++ 계층의 Protocol Buffers — 경로 응답을 파싱하는 구간의 공유 변수를 제거·분리해 탐색 스레드 간 데이터 불일치를 없앰
  • JNI 양방향 호출 — Kotlin이 엔진을 부르고 엔진이 다시 JVM을 콜백하는 구조라, 그 구간의 스레드 어태치 생명주기(GetEnv → AttachCurrentThread → DetachCurrentThread)까지 처리
다른 팀이 일주일째 쫓던 크래시 원인을 하루 만에 찾아냄크래시 대응변경부터 되돌려 사용자 피해를 막고, 원인은 최근 변경 안에서 찾아 재배포
  • 일부 기기에서 안전운전모드에 들어가면 몇 초 만에 앱이 꺼졌다 — 승용 앱에서 가져온 변경이 들어간 뒤 발생. 다른 팀도 같은 증상을 일주일째 추적 중
  • 로그에 찍힌 위치는 죽는 곳일 뿐 — 메모리가 깨진 곳은 따로 있었음
  • 롤백 먼저 — 이미 사용자에게 나간 상태라 변경부터 통째로 되돌림
