AFTER신규 기능과 프로토콜 수정은 Kotlin·코루틴 위주로 작업, 레거시는 수정 빈도 기준 순차 전환 — Kotlin 비율 과반(52%), 회귀 0건

혼자 유지보수하는 3년 차 코드베이스를 한 번에 새로 짤 수는 없었다. 그래서 기준을 나눴다 — 신규 기능을 만들거나 기존 네트워크 프로토콜을 수정할 때는 코루틴 위주로 작업하고, 손대지 않는 레거시 콜백 코드는 그대로 뒀다. 수정이 필요한 프로토콜에 콜백이 중첩돼 있으면 그 콜백 지옥도 함께 코루틴으로 전환했다 — 콜백 기반이던 구글 로그인은 Credential Manager 전환과 함께 Firebase의 Task를 await()로 감싸 suspend 흐름으로 정리했고, 포인트·다중경유지 상태 조회 같은 신규·수정 API는 처음부터 suspend function으로 설계했다. Kotlin 전환도 같은 기준을 따랐다 — 신규 개발은 전부 Kotlin, 레거시는 자주 손대는 코드부터 포팅해 수정할 때마다 null 안전성을 확보했다. 전면 재작성이 아니라 손대는 곳부터 위험을 관리하며 갚아나가는 방식을 택했고, 그 결과 코드베이스의 Kotlin 비율은 52%까지 올라왔다 — 운영과 병행하면서도 회귀는 0건이다.

화면 대부분을 OpenGL로 직접 그리고 경로 탐색·맵매칭이 C++ 엔진에서 도는 앱이라, 크래시가 Kotlin 스택트레이스에 잡히지 않는 계층에서 났다. 특정 GPU(Adreno)에서만 터지던 지도 크래시는 렌더링 방식이 원인이어서 client vertex array를 VBO로 마이그레이션해 근본 해결했다. 나머지는 대부분 동시성 문제였다 — 렌더 스레드가 경로 정점 배열을 읽는 동안 워커 스레드가 그 배열을 해제·교체해 터지던 use-after-free는 정점 배열에 전용 락을 걸어 막았고, 맵매칭의 shared_ptr refcount 레이스는 대입을 std::move로 바꾸고 진입점에 lock_guard를 걸어 해결했다. 워커 스레드가 중복 생성돼 발생한 double-free는 초기화 재진입 가드로 차단했다. 다만 락을 넓게 걸면 프레임이 끊기기 때문에 범위는 최소화하는 쪽으로 잡았다. 네트워크도 C++ 계층에서 다뤘다 — 경로 응답을 Protocol Buffers로 파싱하는 구간의 공유 변수를 제거·분리해 탐색 스레드 간 데이터 불일치를 없앴다. Kotlin과의 경계는 JNI로, 네이티브 워커 스레드가 JVM으로 콜백할 때의 스레드 어태치 생명주기(GetEnv → AttachCurrentThread → DetachCurrentThread)까지 직접 처리했다.

MediaRecorder(AAC) 녹음 → 서버 전송 → 소켓 수신 알림 → MediaPlayer 재생으로 이어지는 송수신 파이프라인 전체를 설계했다. 어려운 지점은 동시성이었다 — 여러 사람이 동시에 보내지만 재생은 하나씩 순서대로 되어야 한다. 수신한 음성을 재생 큐에 쌓고, 큐의 add·poll이 반드시 단일 진입점 하나만 거치게 만든 뒤 락으로 감싸 동시 접근을 차단했다. 재생에 실패한 음성은 큐 앞으로 되돌려 순서를 보존하고, 큐에 상한을 둬 무전이 몰려도 메모리가 무한히 늘지 않게 했다. 재생은 별도 백그라운드 스레드가 짧은 주기로 상태를 확인해 다음 음성으로 넘기고, 길안내·통화 음성과 겹칠 때는 오디오 포커스로 조정했다. 녹음과 재생이 동시에 일어나거나 같은 음성이 중복 전송되던 문제도 이 구조로 정리했다.
